## Objective
Build a greenfield, standalone Node/TypeScript package at `tenant-stacksim/` that fakes a Microsoft GCC High tenant well enough that **Stamper, AO, and EO run their real code, unmodified, against it** — stamping baselines, executing AO commands, and collecting EO evidence — while every object created/mutated/served is logged to an append-only ledger and held for later query. Phase A only (choke-point fake); an HTTP Graph/ARM emulator is Phase B, explicitly deferred.

## Goal Document — G-STACKSIM-1
**Definition of Operational Capability (DOC):** the simulator is operationally complete when, against a running `m365_azure`-profile sim tenant, with **zero code edits** to `ces-eo`, `ces-ao`, or `ces-stamper`:
1. Stamper stamps one baseline entry onto the sim tenant using Stamper's own baseline-stamping template for an authorization-policy-class control (Stamper's template source is separate from AO's `TemplateRegistry.ts`; the exact template is identified by the M4 coding-expert via a targeted read of Stamper's own template file — out of this plan's read scope). The mutation is visible in the object store on re-read.
2. EO's `ComplianceSignalFetcher.fetchAuthorizationPolicy()` (part of `fetchAllSignals()`) runs unmodified against the sim tenant and returns a `SignalResult` with `signalId: 'authorizationPolicy'` and `status: 'success'` (not `'error'`/`'not_assessed'`) — the exact field/value pair confirmed by reading `ComplianceSignalFetcher.ts:391-405`.
3. AO's `A-18` command (`TemplateRegistry.ts:59-62`, a single `Invoke-MgGraphRequest -Method PATCH -Uri '/v1.0/policies/authorizationPolicy'`) executes unmodified against the sim tenant; the mutation appears both as a `Get-MgAuditLogDirectoryAudit`-readable entry in the sim's `auditLogs/directoryAudits` collection **and** as a corresponding entry in the sim's own `ledger.jsonl`.
4. All of the above is reproducible via one CLI command (`stacksim verify-doc`) that seeds a fresh tenant, runs the three checks, and exits 0 only if all pass.

**On checks 1 and 3 targeting the same control via two different callers:** this is intentional, not redundant — check 1 proves Stamper's independent template/session path reaches the sim's `authorizationPolicy` resolver; check 3 proves AO's `TemplateRegistry` path reaches the same resolver via its own distinct command (`A-18`). Both must independently succeed against the identical store object; that dual-path agreement is itself part of the DOC, not incidental overlap.

Loop exit condition = DOC satisfied (M6 gate green).

## Core Design

**(a) Ledger** — `ledger.jsonl` under `.stacksim/tenants/{slug}/`, one JSON object per line, append-only, never rewritten. Fields: `ts`, `type` (`create`|`mutate`|`read-serve`), `objectType`, `objectId`, `actor` (`stamper`|`ao`|`eo`|`probe`), `source` (cmdlet or URI), `milestone`, `sessionType`, `requestId`. `Ledger.query({type, objectType, id, from, to, actor})` streams and filters the file.

**(b) Object store** — one JSON file per tenant-profile instance under `.stacksim/tenants/{slug}/store.json`, collections keyed by object type matching the Object Surface list in the Vault.

**(f) Concurrency & single-writer authority (new — closes the store/ledger race).** Stamper, AO, and EO can run concurrently against the sim (Vault v1 scope). To eliminate lost writes and stale reads without OS-level file-locking:
- **The `stacksim serve` process is the sole owner of `store.json` and `ledger.jsonl`.** No other process — including the CLI's `query-ledger`/`query-evidence`/`seed` commands after M2 — reads or writes those files directly. All access goes through the server's HTTP surface (`/resolve`, `/ledger`, `/evidence`). This is the fix for the "dual in-memory-cache/CLI direct access" ambiguity flagged in gap analysis: there is no second path.
- **Within the server process**, `Ledger.append()` and `ObjectStore.write()` are serialized through a single `Promise`-chained write queue (one `fs.promises.appendFile`/`writeFile` in flight at a time, next call awaits the previous). This makes Windows NTFS append-atomicity a non-issue by construction — there is never more than one OS-level writer, so there is nothing to interleave or tear, independent of whether NTFS itself gives POSIX-style `O_APPEND` guarantees.
- In-memory read cache in `ObjectStore` is coherent by construction (same process, same queue) — the earlier "in-memory cache with debounced fsync" wording is retired since it implied a second access path; the cache is now purely a same-process read optimization behind the single writer.
- `seed`/`init-tenant` (M1) start the server if it isn't already running (or fail with a clear error instructing the operator to run `stacksim serve` first) rather than writing store files themselves.

**(c) Evidence hold** — every resolver invocation that serves data (GET-shaped) writes an immutable snapshot (`request`, `response`, `ts`, `sessionType`, `milestone`) to `.stacksim/tenants/{slug}/evidence/{requestId}.json` via the same server-owned write queue, indexed in the ledger by `read-serve` entries.

**(d) Session-host / TenantProbe compatibility strategy — PSModulePath shadowing with real module names (primary), Node stdin/stdout emulator (Plan B, conditional).**
`session-host.ps1` and `TenantProbe.psm1` are both unmodified, real PowerShell. PowerShell resolves `Import-Module <Name>` by **literal folder/manifest name** against `$env:PSModulePath` — a module directory named anything other than the real name (e.g. the v1 draft's `Stacksim.Graph`) cannot satisfy `Import-Module Microsoft.Graph.Authentication`. **Corrected design:** the sim ships one fake module directory per **real** module name actually referenced by the quotes in Context Summary above (`Microsoft.Graph.Authentication` + 12 Graph submodules, `Az.Accounts`, `Az.Monitor`, `Az.Storage`, `ExchangeOnlineManagement`, `Microsoft.Online.SharePoint.PowerShell`), each with a `.psd1` manifest. Where a real import pins a version (`Microsoft.Graph.Authentication` → `2.35.1`, exact quote above), the fake `.psd1`'s `ModuleVersion` matches exactly.
- **`$env:PSModulePath` is replaced, not prepended, with exactly `<simRoot>\psmodules;$PSHOME\Modules`**, for every `powershell.exe` child process the sim spawns (for spike tests, and later for any real `session-host.ps1`/`TenantProbe.psm1` invocation pointed at a sim tenant). Prepending would still let PowerShell fall through to a real installed SDK module if a given fake module is missing or incomplete — silently hitting a real tenant is the one failure mode this design must foreclose, so replacement (not prepend) is kept for the sim's own module root.
  - **`$PSHOME\Modules` is deliberately retained (gap analysis round 2), not dropped.** A truly full replacement would also remove PowerShell's engine built-in modules (`Microsoft.PowerShell.Utility`, `.Management`, `.Security` — supplying `ConvertTo-Json`, `Test-Path`, string ops, etc., used throughout `session-host.ps1`'s REPL loop and `TenantProbe.psm1`'s logic) from resolution, resting on an unverified assumption about how PowerShell's command-discovery autoload interacts with `$env:PSModulePath` for those modules. Two options were weighed: (a) drop `$PSHOME\Modules` and spike-test that built-ins still resolve regardless, or (b) keep `$PSHOME\Modules` in the replacement list explicitly. **Chosen: (b)** — it is a one-line, zero-risk fix that sidesteps the need to verify an engine-internals assumption at all, because real Microsoft.Graph/Az/Exchange SDKs install via `Install-Module` into user/AllUsers module paths (`Documents\PowerShell\Modules`, `Program Files\PowerShell\Modules`), never into `$PSHOME\Modules` (reserved for inbox engine modules) — so the no-real-tenant-fallthrough guarantee is fully preserved while the risk is removed at the source instead of tested around.
  - Any coverage gap in the fake modules still fails loudly (`Module not found` / `command not recognized`), which remains the desired failure mode: it shows up as a red test, not a live-tenant side effect.
  - As cheap regression insurance regardless of the above, M2's spike test also runs a short builtin-surface smoke check (`ForEach-Object`, `Where-Object`, `Test-Path`, string ops, `ConvertTo-Json`) inline with the shadowed-module check.
  - **The `BLOCKED.md` halt contract is generalized beyond M2/M2b:** any milestone M3–M6 whose test gate fails with a PowerShell `CommandNotFoundException`/`Module not found`-class error against a builtin (as opposed to a sim-owned fake-module cmdlet) writes the same `docs/context/BLOCKED.md` marker (failure output + a proposed fix) and the loop halts exactly as on an M2 failure — closing the gap where a builtin-resolution failure surfacing only at M3+ previously had no halt mechanism.
- **Cmdlet-pattern → resolver table** (`ResolverTable.ts`), two entry kinds, unchanged from v1 in substance:
  1. **Named-cmdlet entries** — `{ cmdlet: 'Get-MgIdentityConditionalAccessPolicy', endpoint: '/identity/conditionalAccess/policies', collection: 'caPolicies', verb: 'GET' }`, mirroring `ComplianceSignalFetcher.endpointToCmdlet`'s map 1:1. Codegen (`generatePsModule.ts`) emits one thin wrapper function per entry, all placed in the `Microsoft.Graph.Authentication` fake module (see File Inventory) since it is guaranteed to load first and PowerShell function export is global regardless of which module technically defines it.
  2. **Generic URI-pattern entries** — path templates with verb → collection CRUD op, used by the single `Invoke-MgGraphRequest` wrapper function, covering `TemplateRegistry.ts` writes and any GET not covered by a named cmdlet.
  All wrapper functions POST `{cmdlet or uri, method, args}` to the `stacksim serve` process's `/resolve` endpoint (single-writer server, see (f)) and return the JSON result.
- **M2 spike test is the proof, and it is binary** (`tests/protocol/psmodule-shadow.spike.test.ts`): spawn real `powershell.exe` with `$env:PSModulePath` replaced by `<simRoot>\psmodules;$PSHOME\Modules`, run the exact `GRAPH_MODULE_IMPORTS` lines quoted in Context Summary verbatim, then `Get-MgIdentityConditionalAccessPolicy | ConvertTo-Json -Depth 5` plus the builtin smoke check above, assert the JSON matches a seeded fixture. Exit 0 = pass, proceed to M3. Non-zero = fail.
- **Loop-halt mechanism on M2 failure:** the M2 milestone script writes `docs/context/BLOCKED.md` containing (1) the spike test's actual failure output, (2) the Plan B proposal (env-gated branch in `ces-shared/scripts/session-host.ps1`, ~6 lines, additive, default-off via `TENANT_STACKSIM_MODE=1`), and (3) a literal `- [ ] Human sign-off to implement Plan B` checkbox. The `/loop` runner's contract: **at the start of every iteration, check for `docs/context/BLOCKED.md`; if present, do not start M3 or any later milestone — surface the file's contents and stop.** A human resolves this by either fixing the shadowing approach directly (then deleting `BLOCKED.md`, loop resumes at M2's spike test) or checking the sign-off box (then M2b, listed as a conditional row in the ladder, becomes eligible for one loop iteration; on M2b's own gate passing, `BLOCKED.md` is deleted and the loop resumes at M3). This is the only place in the ladder where a milestone is not autonomously loopable by design.

**(e) Stack-shape gating.** `StackShapeGate` consults the active profile's `TenantStance`. Two independent layers, per gap analysis's request to test this as behavior, not just data:
1. **Seed-data absence** (M1, already planned): `m365_only` seeding never creates Azure-domain objects; `m365_sentinel` seeding creates only the Sentinel-scoped subset defined below; `m365_azure` seeding creates the full Azure object list from the Vault.
2. **Invoke-time enforcement** (M1, new explicit test): every `ResolverTable` entry carries an `azureTier: 'none' | 'sentinel' | 'full'` field (replacing the earlier boolean `requiresAzure`), ordered `none < sentinel < full`. `StackShapeGate` allows a resolver call only when the active profile's tier is `>=` the resolver's tier; otherwise it throws before touching the store, surfaced to PowerShell as a normal cmdlet exception (matching how a real tenant would 403/404 a call outside its licensed surface).

**`m365_sentinel`'s exact Azure surface (gap analysis round 2 — the Vault's Object Surface list groups `m365_azure`/`sentinel` together and doesn't fully disambiguate per shape; this is an explicit architect judgment call, not a Vault-sourced fact):** Sentinel is a Log-Analytics-workspace-hosted SIEM solution and does not require the rest of the Azure infra list to function. `azureTier: 'sentinel'` covers **only** Log Analytics workspaces and Sentinel-solution/workspace-linked objects (e.g. a `Get-AzOperationalInsightsWorkspace`-class resolver and a Sentinel-solution-status resolver). Storage accounts, Key Vaults, automation accounts, VNets/NSGs, and managed identities remain `azureTier: 'full'` and are **denied** under `m365_sentinel`, identically to `m365_only`.

`StackShapeGate.test.ts`'s behavioral matrix (three shapes × two resolver classes, six assertions):

| Profile | Sentinel-tier resolver (Log Analytics / Sentinel) | Full-tier resolver (storage/KeyVault/VNet/automation/managedIdentity) |
|---|---|---|
| `m365_only` | throws | throws |
| `m365_sentinel` | succeeds | throws |
| `m365_azure` | succeeds | succeeds |

## Testing Strategy
- **Unit (Vitest):** one `*.test.ts` per module in `src/` — pure logic, no PowerShell spawned. Includes the M0 concurrency test (50 concurrent in-process appends, no corruption) and the M1 `StackShapeGate` throw/succeed pair.
- **Protocol contract tests:** golden transcripts under `tests/protocol/goldens/` — spawn real `powershell.exe` with `$env:PSModulePath` replaced, feed exact command strings lifted from `ComplianceSignalFetcher.ts`/`TemplateRegistry.ts`, assert stdout matches expected JSON shape. `psmodule-shadow.spike.test.ts` (M2) is the load-bearing member of this set.
- **Integration gates:** one test per milestone row (M1–M6), each independently runnable; M6 is the DOC gate and the loop's exit condition. M2b's gate (conditional) reruns the same spike-test intent against Plan B.
- Manual/optional: M6's use of unmodified `ces-eo`/`ces-ao`/`ces-stamper` code is driven purely by `$env:PSModulePath` replacement + existing `TENANT_SLUG`/`TENANT_CONFIG` env overrides (Vault-documented) — no code changes, just environment.

## Out of Scope (v1)
- HTTP Graph/ARM emulator (Phase B).
- `tenant-tests`/EUT suite support beyond what M3 yields for free (only the one named UC-A.identity.ps1 Graph assertion is a gate; not all 9 UC cases).
- Performance/scale (single-tenant, dev-box only, one server process).
- Real cert-based auth, token expiry simulation, throttling/429 simulation.
- Any edits to `ces-eo` (hard constraint) or, absent explicit sign-off, `ces-shared` (M2b only).
- SharePoint/Teams cmdlet coverage beyond empty pass-through import stubs.

## Architecture Decisions
- **Workspace membership: standalone**, not joined to the root npm workspace (root `package.json`'s `workspaces`/`test`/`build` scripts explicitly enumerate members by name; joining would require editing it for no functional benefit).
- **Real module names, full `$env:PSModulePath` replacement over prepend or script replacement:** the only mechanism proven zero-touch to both choke points simultaneously, and the only one that fails loudly on coverage gaps instead of silently falling through to a real tenant.
- **Single-writer server process over multi-process file access:** removes the store/ledger race and the Windows append-atomicity question by construction rather than by relying on OS-level file-locking semantics.
- **Resolver table is the single source of truth**, codegen'd into real-named PowerShell modules.
- **M2 is the one non-autonomous milestone in the ladder**, by design — a `BLOCKED.md` marker file is the explicit, human-in-the-loop halt/resume mechanism for `/loop` (generalized to M3–M6 builtin-resolution failures too, v3).
- **`$PSHOME\Modules` retained over full built-in removal:** a one-line safer fix beats spiking/asserting an unverified PowerShell engine-internals fact; real SDK installs never live under `$PSHOME\Modules`, so the isolation guarantee is unaffected.
- **`m365_sentinel` modeled as a distinct, narrower Azure tier via an ordered `azureTier` field, not a second boolean:** keeps gating logic uniform across all three shapes and leaves room for a future tier without re-touching every resolver.
