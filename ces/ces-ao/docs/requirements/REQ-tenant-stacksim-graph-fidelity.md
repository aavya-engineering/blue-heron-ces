- **From:** ces-ao (W4-AO4 95-op matrix, 2026-09-27)
- **To:** tenant-stacksim (resolvers + seed; acceptance input to `GOAL-AO-SIM-COVERAGE-2026-09-26.md`)
- **Status:** MET (2026-09-28, FC-AO-2) — the 95-op matrix on the fixed sim shows 0 ops open against this REQ (`docs/AO-95-OP-MATRIX.md`: PASS 94 · HONEST-OPEN 1 · FAILING 0; the one open op, B-08, is `REQ-tenant-stacksim-ao-paired-read-endpoints`)
- **Evidence:** `ces-ao/docs/AO-95-OP-MATRIX.md` (generated by `test/integration/ao95.matrix.stacksim.test.ts`, stacksim `m365_azure`, dist of branch `gp-demo-1-stacksim-p02` @ 9170eb8)

## What

Microsoft Graph (`*-Mg*` cmdlets, `Invoke-MgGraphRequest`) ops that AO runs correctly but that the sim cannot answer semantically.

AO behaved correctly on every op below: the governed pipeline ran, the command reached the sim through the shims,
exactly one contract-conforming evidence row was written per request, and every applicable deny was proven. What is
missing is on the sim side: the response does not contain what the command needs, or the write does not land where the
paired read looks. Since W4-AO1, AO records the REAL before/after state, so a write that "succeeds" without changing
what its read observes is now visible (pre == post) instead of hidden behind a placeholder.

## Root causes seen (most important first)

1. **`-UserId '<UPN>'` resolves to the wrong user.** `Update-MgUser`, `Remove-MgUser`, `Revoke-MgUserSignInSession` called with a
   UPN act on `user-1` regardless of the UPN (stdout shows `id: user-1` next to `userId: sim.user4@...`). Real Graph accepts a
   UPN as the user key. Impact: A-02/C-06/H-02 writes never land on the target, and **A-03 (hard delete) deleted `user-1`, not the
   requested `sim.user5`** — a destructive op hitting the wrong object is the worst kind of sim infidelity. Resolve `{id|userPrincipalName}`.
2. **POST to a collection breaks the collection read.** After `Invoke-MgGraphRequest -Method POST /v1.0/deviceManagement/deviceCompliancePolicies`
   (B-13) or `.../windowsAutopilotDeploymentProfiles` (B-14) a GET of the same collection no longer returns `{ value: [...] }`
   ("Property \"value\" cannot be found"): the new object is stored under the collection name as its id.
3. **Unsupported write endpoints return HTTP 500:** `POST /v1.0/roleManagement/directory/roleEligibilityScheduleRequests` (A-10).
4. **State changes not reflected in the paired read:** retire/wipe (B-05), rename/sync (B-01), device isolation (H-03), per-user
   MFA requirement (A-07), group membership moves (A-04), risky-user confirmation (A-16, C-10), app password rotation (C-02).
5. **Seed gaps (reads return nothing):** guest users (A-12); PIM eligibility schedules / role assignments carrying the built-in
   role definition ids, e.g. Global Administrator `62e90394-69f5-4237-9190-012177145e10` (A-09, C-04; AO binds these ids per
   W4-AO2); applications with password/key credentials, some expiring within 30 days, with owners (C-01, C-02, C-08); risky users
   (A-16, C-10, H-02); device compliance policy device statuses (B-04); personally owned devices (B-11); Autopilot deployment
   profiles (B-12); secure score control profiles (F-02, F-09); device configurations under the name AO reads (F-03); service
   principal app role assignments (F-10); Unified (Teams) groups (D-08); security alerts (H-08); users with the fields G-08 filters on;
   a duplicate CA-policy pair so A-20 has something to dedupe (today only the coverage harness seeds it).
