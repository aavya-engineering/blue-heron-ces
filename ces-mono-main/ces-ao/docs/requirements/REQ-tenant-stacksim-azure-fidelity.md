## What

Azure ops (`Get-Az*`/`Set-Az*`/`New-Az*`, `az ...` via the az shim) that AO runs correctly but that the sim cannot answer semantically.

AO behaved correctly on every op below: the governed pipeline ran, the command reached the sim through the shims,
exactly one contract-conforming evidence row was written per request, and every applicable deny was proven. What is
missing is on the sim side: the response does not contain what the command needs, or the write does not land where the
paired read looks. Since W4-AO1, AO records the REAL before/after state, so a write that "succeeds" without changing
what its read observes is now visible (pre == post) instead of hidden behind a placeholder.

## Root causes seen

1. **`az keyvault key show|rotate` returns HTTP 500 from the az shim** (C-03). AO's get-then-set therefore refuses to write
   (never blind-write). Seeded key `keyVaultKey-1` has no `name`; AO asks for the key named in the request (`sim-storage-key-1`, the tenant's `cmk_key_name`).
2. **Writes not reflected in the paired read:** F-13 (route table + blackhole route + NSG association: the read of the VNet's
   subnets still shows `subnet: null, nsg: NONE, routeTable: NONE` — the seeded VNets have `Subnets: []`, seed at least one
   workload subnet); F-14 (`New-AzNetworkWatcherFlowLog`: the read still counts 0 flow logs — seed a NetworkWatcher and persist flow logs);
   C-09 (directory setting / banned-password update not visible through `Get-MgDirectorySetting` / the read).
