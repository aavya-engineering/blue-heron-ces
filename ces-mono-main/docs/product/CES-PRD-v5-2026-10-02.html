0.1 How to read this document

  • Binding words. "Shall" marks a requirement. Everything else is explanation.
  • Requirement IDs. Each ID names a module and a type:
    • MU-FR-01 is a functional requirement of Muster;
    • MU-NFR-01 is a non-functional one (security, reliability, operability);
    • IF-MU-ST-01 is a hand-off from Muster to Stamper;
    • EV-FR-01 is an audit-evidence requirement.
    Module codes are in the glossary (§19).
  • Priority. One scheme for the whole document, tied to the release it belongs to:
    • Must: the first release (V1). V1 does not ship until every Must requirement passes.
    • Should: the next release.
    • Could: a later release.
  • Verification.
    • Test: an automated test passes.
    • Demonstration: an operator shows the behaviour on a named environment.
    • Inspection: a reviewer checks an artifact against the stated criterion.
  • Evidence rungs. Proof comes at four levels:
    1. unit tests;
    2. tenant-stacksim, the CES simulated tenant;
    3. a live Microsoft GCC or GCC High test tenant;
    4. a live production tenant.
    An acceptance criterion that names no rung is met at rung 2. V1 requires rung 3 for every Must requirement that reads or changes a tenant (§15.1). Rung 4 is credited only to earlier builds, which configured a live tenant in March–April 2026, and is always marked "earlier build".
  • Controls. Numbers such as 3.1.4 are NIST SP 800-171 Rev 2 requirements, the baseline CMMC Level 2 assesses. A requirement's Controls field names customer controls it helps the contractor meet. Its CES controls field names controls CES itself must meet, because CES runs inside the assessed enclave. §13 is generated from these two fields.

1. Summary

Defense contractors that handle Controlled Unclassified Information (CUI) must meet the 110 security requirements of NIST SP 800-171 Rev 2 to earn CMMC Level 2, and must prove it to an assessor. Most small and mid-sized contractors lack the staff to do four things:

  • find their gaps;
  • configure a Microsoft GCC or GCC High tenant to close them;
  • keep daily administration from reopening them;
  • hand the assessor evidence for every requirement.

CES does that work for them.

  • Muster measures readiness and writes the remediation plan.
  • Stamper configures the tenant to the plan and checks each change.
  • AdminOps puts every later admin change through scope, boundary and two-person checks, and records evidence.
  • EvidenceOps keeps the evidence, the security plan (SSP), the plan of action (POA&M) and the SPRS score current, and gives the assessor a read-only view.
  • ces-shared holds the contracts that connect them.

The first release (V1) targets Microsoft GCC and GCC High; GCC High is required wherever the contractor holds ITAR or other export-controlled data. CES uses the simulated tenant for demos and testing, and touches a live tenant only when an engagement is cleared for live access. It never counts a requirement as met without observed evidence from that customer's own tenant. No CUI ever flows from a customer tenant into a BHD system (SYS-FR-13).

Where CES runs is an open decision. The first live tenant was configured remotely, with all CES software running on a development workstation. Before V1, BHD must decide where each module runs (inside the customer's enclave, operated by BHD outside it, or split) and what work each choice takes. §6.1 sets out the options; SYS-NFR-18 requires the decision record.

2. Problem and evidence

Problem Evidence
Contractors must implement 110 requirements and demonstrate each one to an assessor. 32 CFR Part 170 makes NIST SP 800-171 Rev 2 the CMMC Level 2 requirement set, and SP 800-171A (June 2018) its assessment objectives [S3, S4, S5]. DFARS 252.204-7012 requires covered contractors to implement SP 800-171 and to report cyber incidents within 72 hours [S8].
Contractors do not know their starting position, yet a senior official must affirm the score they report. A Level 2 self-assessment is reported in SPRS and affirmed by a senior official of the contractor [S5].
Configuring Microsoft 365 GCC or GCC High, and the paired Azure cloud, to the 110 requirements takes specialist knowledge. The settings span identity, devices, data protection, logging and network. Each area needs its own PowerShell or Graph session.
After the baseline, routine admin changes drift the configuration and leave no record of who approved what. Requirements 3.1.4 (separation of duties), 3.4.3 (track and approve changes) and 3.3.2 (trace actions to users) apply to every later change.
Evidence, the SSP and the POA&M are assembled by hand and go stale between assessments. Certification artifacts must be hashed and kept for six years from the CMMC Status Date (32 CFR 170.17) [S5].

Why one product. Each problem feeds the next. The gaps define the configuration, the configuration sets the baseline, and the baseline is what every later change must protect and every piece of evidence must prove. CES keeps that chain in one system. The plan Muster writes is the plan Stamper runs. The evidence Stamper and AdminOps record is the evidence EvidenceOps scores and shows the assessor.

6.1 Deployment model: an open decision

Why this is open. The first live tenant was configured remotely: every CES module ran on a development workstation and reached the tenant over Microsoft's APIs. That proved the product works. It did not decide where each module should run for customers. Each module can run in one of three places, and each choice needs different work. BHD must choose per module before V1 (SYS-NFR-18) and record why.

Placement What it means Main advantage Main cost
Inside the customer's enclave The module runs on infrastructure the customer controls, under the customer's authorization. CUI and evidence never leave the customer's boundary. A deployment, update and support channel into every customer.
Outside, operated by BHD The module runs in BHD systems and reaches the customer tenant over Microsoft's APIs, as in the first live run. One deployment to operate and update for all customers. Allowed only for data ruled not CUI (SYS-FR-13). BHD holds privileged access to many tenants.
Hybrid Collection or storage runs inside; orchestration runs outside. Keeps any CUI inside while centralizing operations. Two sets of work, and every split flow must be classified.

The deciding question. Can control-plane metadata (tenant settings, policy states, role assignments, audit configuration) and the evidence, SSP and scores derived from it be ruled not CUI (OQ-11)? If yes, outside and hybrid placements are open. If no, any module that stores or processes that data must run inside.

Advisory — not a requirement. This statement summarizes the remote-control advisory of 2026-09-29. It informs the deployment decision (founder decision 23). It is not legal advice, and the decision record (SYS-NFR-18) still decides.

Answer. BHD can plan, configure and administer a client's Microsoft tenant from a BHD control point, on two conditions:

  1. No CUI reaches BHD. Settings, policies, identities and security logs may; files, email and other CUI content may not (SYS-FR-13).
  2. The control point itself meets CMMC Level 2, because it sits inside every client's assessment scope (SYS-NFR-19).

Why. Under 32 CFR 170.19(c)(2), an external service provider that is not a cloud service provider and handles security protection data without CUI has its services assessed as security protection assets within each client's assessment. It needs no FedRAMP authorization, but it must be documented in the client's SSP and in a customer responsibility matrix [S9, S10]. Security protection data includes configuration data, log files, and data on the configuration or vulnerability status of in-scope assets (32 CFR 170.4) [S10]. A provider that handles CUI in the cloud must instead meet FedRAMP Moderate or equivalent under DFARS 252.204-7012 [S8].

Module Runs at a BHD control point? Reason
Muster Yes Interview, plan and read-only discovery of settings are planning data. The interview must not collect CUI details.
Stamper Yes Writes configuration only; earlier builds did this remotely (March–April 2026). Its host becomes a security protection asset in each client's scope.
AdminOps Mostly Identity, device, policy and key operations are control-plane operations. Content-returning operations (eDiscovery, audit searches that show file names or subjects) run inside the client environment or return metadata only (AO-FR-16).
EvidenceOps No: inside the client Evidence and audit logs can contain CUI, and the SSP and POA&M are kept for six years. Only scores and statuses flow out.

Preconditions for remote control.

  • The BHD operational tenant is in GCC High, the clients' cloud, for partner delegated administration (GDAP). Microsoft's current GDAP and cross-cloud rules must be verified first (OQ-13); the Microsoft pages reviewed do not state them [S11, S12].
  • Only verified US persons administer ITAR clients (SYS-FR-15).
  • The control point is hardened to Level 2: privileged access workstations, multi-factor authentication, logging, FIPS-validated encryption and approval of privileged remote commands (3.1.12–3.1.15, 3.5.3, 3.13.11).
  • Data is filtered at the source: only settings and metadata leave the client. Security protection data is generally not CUI, but logs can carry CUI details, so OQ-11 stays open until the classification is recorded.

Working assumption for the deployment options analysis. Muster, Stamper and most of AdminOps may run at a BHD control point. EvidenceOps, the Evidence Collector and content-returning AdminOps operations stay inside the client environment. This is the starting point for the analysis, not the decision: the per-module decision record (SYS-NFR-18) decides.

The decision record (SYS-NFR-18) states, for each module, the chosen placement, every data class it stores or sends and its classification, and the work that placement needs. Requirements in this document are written to hold under any placement, except where they cite the record.

Development switch: a deployment rule. A CES installation has one development switch, off by default. While it is on, the installation may skip the live-access gate (SYS-FR-06), operator passkey sign-in (SYS-FR-07) and two-person approval (AO-FR-08), for development and simulator work only. While the switch is on, the installation refuses every request for a tenant whose record says live. It records every use of the switch, and every request the switch lets past a gate, with the operator and the UTC time. Production never runs with the switch on: every release's deployment definition sets it off, and a production installation refuses to start with it on.

Rationale: founder decision 2026-10-02: the gates slow development and simulator work, so they need an off switch that cannot reach a live tenant.

7. End-to-end journeys

J1. Readiness assessment. Given a BHD operator has registered a contractor's tenant and opened an engagement, when the contractor answers the adaptive interview after discovery on the simulated tenant, then Muster shows a conservative SPRS score, the unmet requirements and a remediation plan, and exports a versioned readiness record.

J2. Live discovery. Given the BHD operator has switched on live access for one engagement, when a contractor Global Reader completes device-code consent, then Muster reads the tenant through read-only calls, records the consent in the readiness record, and prefills interview answers labelled as auto-detected.

J3. Plan to configured tenant. Given a remediation plan for a registered tenant, when the BHD operator pushes the plan and runs it in Stamper against the live tenant, then Stamper applies each change, reads the tenant after each change, records evidence, and returns per-directive verdicts that Muster shows as plan progress.

J4. Governed change with two-person approval. Given a contractor administrator requests a Tier-3 AdminOps operation on a live Level 2 tenant, when a different person, holding an approver token issued by EvidenceOps for that tenant, approves the request, then AdminOps runs the operation once, and EvidenceOps shows the request, the approval, the execution and its verdict.

J5. Continuous evidence and the assessor package. Given configuration evidence, admin evidence, live signals and manual uploads exist for a tenant, when the compliance lead runs an assessment, then EvidenceOps produces a 110-requirement snapshot, the SPRS score, the SSP and the POA&M, and the assessor opens a read-only view and downloads a hashed evidence package.

J6. Physical and procedural evidence. Given a requirement has no automated signal, when the compliance lead uploads the artifact its manual-evidence procedure names, then the Evidence Collector hashes and records it, and EvidenceOps lists it for assessor review without changing any automated verdict.

J7. Prime oversight. Given a prime contractor holds readiness records from its subcontractors, when the prime opens the roll-up, then Muster shows each subcontractor's status and exports the list of subcontractors still pending.

8. System requirements

SYS-FR-01One tenant per record

Priority: Must · Goal: G5 · CES controls: 3.1.1, 3.1.3 · Verify: Test

Every record, evidence item, verdict and document that CES stores or displays shall carry exactly one tenant identity, and CES shall refuse any request that reads or writes data of a tenant other than the one the request names.

Rationale: CES serves many customers at once. Each unique customer configuration is serialised and tagged, so every tool pulls the right file set for the right configuration, and the whole set can be traced and managed as one (founder, 2026-10-02).

Acceptance criteria

  • Given two registered tenants A and B, when any tenant-scoped route is called for tenant A, then the response contains no record of tenant B.
  • Given a session connected to tenant B, when a data route is called for tenant A, then the route returns no signals and reports the tenant mismatch.

SYS-FR-02Dry runs are never satisfied

Priority: Must · Goal: G5 · Controls: 3.12.1 · Verify: Test

CES shall record every dry run with an explicit dry-run mode and shall never count a dry run as satisfying a requirement.

Acceptance criteria

  • Given a dry run of any AdminOps operation or Stamper task, when its evidence is recorded, then the record carries mode "dry run" and a verdict other than satisfied.
  • Given a dry-run evidence record, when EvidenceOps assesses the tenant, then no requirement's status changes.

SYS-FR-03Empty reads are not satisfied

Priority: Must · Goal: G5 · Verify: Test

CES shall record a read that returns no parsable records as not satisfied, including a read whose only output is a session banner or status text.

Acceptance criteria

  • Given a live read that returns zero records, a zero count, blank output or banner text only, when the verdict is computed, then the verdict is not satisfied.

SYS-FR-04Plan intent is not evidence

Priority: Must · Goal: G5 · Controls: 3.12.1 · Verify: Test

CES shall derive every requirement verdict from observed tenant state or uploaded evidence, and shall label a requirement with a planned but unexecuted change as not verified.

Acceptance criteria

  • Given a plan that contains a directive for requirement 3.5.3 and no executed task, when Stamper or EvidenceOps assesses the tenant, then 3.5.3 reads "not verified".

SYS-FR-05Simulator by default

Priority: Must · Goal: G5 · Verify: Test

Every CES module that reads or changes a tenant shall target the simulated tenant unless a live opt-in, scoped to one engagement or one run, is present.

Acceptance criteria

  • Given a fresh installation with no live opt-in, when any module is asked to read or change a tenant registered as live, then it refuses and records the refusal.

SYS-FR-06Gated live access

Priority: Must · Goal: G1 · CES controls: 3.1.5 · Verify: Test

CES shall read a live tenant only after (a) a BHD operator switches on live access for that engagement and (b) a tenant user holding the Global Reader role, plus Azure Reader for Azure reads, completes device-code consent; CES shall record both events in the readiness record. The development switch (§6.1), off by default, may lift this gate for development and simulator work only; it shall be refused for any tenant whose record says live, and every use shall be recorded.

Rationale: founder decisions 2026-09-27 #5 and 2026-09-28 #15, #20.

Acceptance criteria

  • Given live access is off for an engagement, when a live read is requested, then it is refused.
  • Given live access is on and the consenting user lacks Global Reader, when consent completes, then live reads for Exchange, Purview, Azure and Teams stay refused and the reason is shown.
  • Given consent completes, when the readiness record is exported, then it contains the operator who switched live access on, the consenting user, the roles verified and both UTC times.
