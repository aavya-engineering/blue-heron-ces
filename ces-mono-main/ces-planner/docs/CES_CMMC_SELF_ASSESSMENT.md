# CES Toolchain: CMMC L2 Scoping and Self-Assessment Analysis

**Date:** 2026-03-22
**Author:** VFS Advisory — Compliance Engineering
**Classification:** Internal Use Only — Not CUI
**Audience:** VFS Executives, CMMC Advisors, Technical Staff

---

## 1. Executive Summary

The Compliance Engineering Suite (CES) is **definitively out of scope for CMMC Level 2 assessment**. This document explains why, maps the architectural boundary between CES and Stamper, and provides practical guidance for VFS advisors who may face assessor questions about their tooling.

**Key Findings:**

- CES-FE operates entirely offline on the advisor's local machine. It does not process, store, or transmit Controlled Unclassified Information (CUI). It therefore does not meet the definition of a CUI Asset, Security Protection Asset, or Contractor Risk Managed Asset under CMMC scoping methodology.
- The compliance metadata CES generates — gap analysis results, readiness scores, mission plans — is consultant work product, not CUI. It does not carry CUI markings and does not derive from marked CUI source material.
- The CMMC assessment boundary begins at the tenant connection point, where three tools built on Stamper core — **Stamper** (tenant configuration), **AdminOps** (operational management), and **EvidenceOps** (assessment evidence generation) — execute PowerShell and CLI commands against the contractor's M365 GCC High and Azure Government environments. All three likely qualify as External Service Providers (ESPs) and require separate scoping analysis.
- CES's lack of authentication, encryption at rest, and audit logging would be red flags in a CUI-handling system. Because CES is out of scope, these design choices are architecturally appropriate — they reduce complexity for a tool that does not require CMMC controls.
- VFS should invest in advisor training and data handling policies rather than technical hardening of CES. The highest-risk scenario — an advisor pasting marked CUI into CES input fields — is a policy failure, not an architectural one.

## 2. Background

CES is a two-repository CMMC L2 compliance toolchain designed for VFS advisors preparing Defense Industrial Base (DIB) contractors for certification:

**CES-FE** (`cse-fe-v2`) is an offline-first React single-page application. Advisors work through three sequential tools — the Strategic Intent Tool (SIT), the Readiness Recon Tool (RRT), and the Mission Planning Tool (MPT) — answering question banks that produce immutable JSON artifacts. These artifacts capture compliance goals, evaluate the contractor's readiness posture, and generate actionable remediation plans. All data persists locally in the browser's IndexedDB database (named `CMMCComplianceTool`) via the Dexie library. The application loads static YAML question banks and JSON schemas from the `/public/data/` and `/public/schemas/` directories. It makes no network calls to external APIs, cloud services, or contractor environments.

**Stamper** (`stamper`) is a Node.js orchestration engine used by BHD consultants to configure the contractor's tenant exactly to the agreed-upon plan. It consumes mission plans generated by CES-FE, resolves them against command registries (126 M365 entries and 70 Azure infrastructure entries), and executes PowerShell and CLI commands against the contractor's M365 GCC High and Azure Government tenants using certificate-based authentication.

**AdminOps (AO)** is built on Stamper core and used by the customer and BHD consultant to manage the tenant operationally — ongoing configuration management, policy enforcement, and tenant health monitoring. It connects to GCC High.

**EvidenceOps (EO)** is built on Stamper core and used by the customer, BHD consultant, and CMMC assessor to generate assessment input — evidence collection, evidence storage, and compliance artifact generation. It connects to GCC High.

All three tenant-connected tools (Stamper, AdminOps, EvidenceOps) share Stamper's core engine, including pre-authenticated PowerShell sessions across six engine types: Microsoft Graph, Exchange Online, Information Protection and Policy Service, Azure CLI, SharePoint Online, and Teams. Each tool services a different persona and use case but shares the same GCC High connection infrastructure.

CES-FE has no runtime dependency on the tenant-connected tools. CES-FE generates plan artifacts; Stamper/AO/EO consume them. The handoff is a file export, not an API call.

## 3. CMMC Scoping Analysis

CMMC Level 2 assessment scoping identifies three categories of in-scope assets:

1. **CUI Assets** — systems that process, store, or transmit CUI.
2. **Security Protection Assets** — systems that provide security functions for CUI assets (firewalls, SIEM, identity providers, endpoint protection).
3. **Contractor Risk Managed Assets** — systems that can, but are not intended to, process CUI and are managed to prevent CUI exposure.

CES-FE does not meet any of these definitions. It runs on the advisor's workstation, not within the contractor's CMMC boundary. It handles compliance planning metadata — questions about the contractor's security posture, gap analysis results, remediation roadmaps — none of which constitutes CUI.

CUI must be explicitly designated and marked per the CUI Registry and NIST SP 800-171. Compliance metadata generated by a consultant's planning tool does not carry CUI markings and does not derive from CUI source material. A readiness posture score of "72% of L2 controls met" is an advisor's analytical work product, not controlled information requiring safeguarding under 32 CFR Part 2002.

The distinction between consultant tools and contractor systems is well-established in CMMC assessment methodology. Assessor laptops, consultant spreadsheets, and advisory planning software are not assessed unless they handle the contractor's CUI or maintain remote access to CUI systems. CES-FE does neither. It operates on the advisor's local machine with no network connectivity to any contractor environment.

**Scope Determination:** CES-FE is out of scope for CMMC Level 2 assessment. No CMMC controls apply. No assessment evidence is required.

## 4. The CES-Stamper Boundary

Data flows through the CES toolchain in a single direction:

```
Advisor Q&A (CES-FE)
  --> SI Baseline artifact (immutable, local IndexedDB)
  --> RR Question Set + Readiness Posture (local IndexedDB)
  --> Mission Plan artifacts (Manual Plan, Exec Plan, Proposal, Tenant Manifest)
  --> [FILE EXPORT — CMMC boundary crossing point]
  --> Stamper ingests mission plan, authenticates to tenant (cert-based auth)
  --> Stamper configures M365 GCC High + Azure Gov per plan
  --> AdminOps manages tenant operationally (customer + BHD consultant)
  --> EvidenceOps generates assessment evidence (customer + BHD consultant + assessor)
```

The CMMC boundary begins at the file export point where the tenant-connected tools (Stamper, AdminOps, EvidenceOps) ingest artifacts and initiate authenticated sessions against the contractor's tenant. Everything upstream of that point — the advisor's question-answering workflow, the artifact generation pipeline, the local IndexedDB storage — is advisor-side planning activity that never touches the contractor's CUI environment.

Mission plan artifacts crossing this boundary are not CUI. They contain remediation instructions (which Exchange Online policies to configure, which Conditional Access rules to deploy, which Sentinel analytics rules to enable) expressed as structured JSON referencing Stamper's command registries. These are implementation specifications authored by the advisor, not information derived from or containing contractor CUI.

Note that EvidenceOps introduces a unique scoping consideration: the CMMC assessor is among its users. EvidenceOps generates assessment input artifacts directly from the tenant, meaning the assessor interacts with a VFS-built tool during the formal assessment process. This strengthens the ESP classification for EvidenceOps specifically.

## 5. Data Sensitivity Analysis

CES-FE persists data in an IndexedDB database named `CMMCComplianceTool` with eleven tables across five schema versions. The following analysis catalogs what each table stores and its sensitivity classification:

**Customer Records** (`customers` table): Contractor name, optional email, optional phone number, target CMMC level, and timestamps. This is basic business contact information — not CUI, but it constitutes Personally Identifiable Information (PII) subject to standard business data protection practices.

**SI Baseline Records** (`si_baselines` table): Strategic intent configuration including target CMMC level, CUI presence designation (`cui_presence` field with values like `cui_present` or `fci_only`), boundary strategy, deployment posture, tenant model preference, licensing tier, user and endpoint counts, and governance roles. These are the advisor's planning inputs about the contractor's *intended* compliance posture. The `cui_types` string array captures *categories* of CUI the contractor handles (e.g., "ITAR", "CDI"), not actual CUI content. This is compliance metadata.

**CUI Boundary Records** (`cui_boundaries` table): Declarations about the contractor's CUI scope — which systems, users, and data flows handle CUI. This describes the boundary but does not contain CUI itself.

**BTC Confirmation Records** (`btc_confirmations` table): Boundary topology confirmation answers, evidence references, risk flags, and gate status determinations. These capture the advisor's assessment of the contractor's boundary configuration.

**Tenant Config Profile Records** (`tenant_config_profiles` table): Tenant identity (tenant ID, primary domain, custom domains), licensing details (SKU, license count, add-ons), identity architecture (admin naming conventions, break glass accounts), privileged access details (global admin names, PIM status), and security configuration metadata. This table contains the most operationally sensitive data in CES — tenant identifiers, admin account names, and security architecture details. While not CUI, this information could aid an attacker if compromised and warrants protection as sensitive business information.

**Policy Inputs Records** (`policy_inputs` table): Organizational metadata, personnel details, organizational-defined parameters (ODPs), and governance information collected for policy document generation.

**Readiness Posture Records** (`readiness_postures` table): Control-by-control assessment results (`met`, `partial`, `not_met`, `unknown`), key findings with severity ratings, evidence references, and aggregate compliance scores. This is the advisor's analytical output — compliance metadata.

**Mission Plan Records** (`mission_plans` table): Generated remediation plans including manual implementation steps, executive proposals, tenant manifests, optional infrastructure manifests, and optional policy documents. These are advisor-authored implementation roadmaps.

**Cache Tables** (`question_banks_cache`, `domain_data_cache`): Cached copies of YAML question banks and domain reference data loaded from the `/public/data/` directory. These contain no customer-specific information.

**Classification Summary:** No table in CES stores CUI. The `tenant_config_profiles` table contains operationally sensitive tenant configuration data that warrants standard business protection. The `customers` table contains minimal PII. All other tables contain compliance metadata — the advisor's planning and analytical work product.

## 6. Architectural Strengths

If a CMMC assessor were to evaluate CES-FE — which they would not, since it is out of scope — they would observe several security-relevant design patterns:

**Offline-first architecture with no network attack surface.** CES-FE makes no API calls, no WebSocket connections, and no authenticated requests to external services. The only network activity is loading static YAML and JSON files from the application's own `/public/` directory during initial startup. This eliminates entire categories of attack vectors: man-in-the-middle interception, API credential theft, session hijacking, and cross-site request forgery.

**Immutable SI Baselines with version tracking.** Once generated, SI Baseline artifacts are marked immutable (`isImmutable: true` in the `si_baselines` table). Downstream artifacts — RR Question Sets, Readiness Postures, and Mission Plans — reference their parent baseline by ID through a strict dependency chain. This prevents unauthorized modification of the compliance foundation after it has been established.

**Schema validation via AJV before persistence.** Every generated artifact is validated against CES JSON schemas (loaded from `/public/schemas/`) before being written to IndexedDB. Malformed or tampered artifacts are rejected at the validation boundary. This enforces data integrity across the artifact chain.

**Artifact provenance tracking.** Each artifact carries a `ces` metadata header recording the artifact type, schema version, generation date, and (for downstream artifacts) references to parent artifacts via `ArtifactRef` objects containing `schema_id`, `artifact_id`, `version`, and `hash_sha256`. This creates a verifiable chain of custody from strategic intent through mission plan generation.

**Scoped data access via compound indexes.** IndexedDB queries use compound indexes (e.g., `[customerId+baselineId]`) to scope data access to the correct customer and baseline combination. This prevents accidental cross-customer data leakage within the local database.

**Zustand state isolation with namespaced persistence.** Application state is segmented across purpose-specific Zustand stores, each persisted under a distinct `localStorage` key (`ces-app-store`, `ces-sit-store`, `ces-rrt-store`, `ces-cui-store`, `ces-btc-store`, `ces-tcp-store`, `ces-policy-store`). This prevents state corruption across workflow stages and allows targeted state resets.

## 7. Architectural Weaknesses

The following characteristics would be security concerns in a CUI-handling system. Because CES is out of scope, they are documented here for completeness, not as remediation requirements:

**No authentication or access control.** CES-FE has no login screen, no user identity verification, and no role-based access control. Anyone with access to the advisor's file system can open the application and read all customer data in IndexedDB.

**No encryption at rest.** IndexedDB stores all data as plaintext JSON in the browser's local storage. Customer records, tenant configuration profiles, readiness postures, and mission plans are readable by any process with file system access to the browser's profile directory.

**No audit logging.** CES-FE does not record who accessed, created, modified, or exported artifacts. There is no trail of advisor activity beyond the `createdAt` and `updatedAt` timestamps on database records.

**No data loss prevention controls.** CES-FE does not scan input fields for CUI markings, classification banners, or sensitive data patterns. An advisor could paste marked CUI into any free-text field without warning.

## 8. Risk Scenario: Advisor Misuse

The primary risk scenario for CES is an advisor pasting actual marked CUI — excerpts from classified documents, contractor SSP content containing CUI markings, or controlled technical data — into CES input fields.

**Impact:** If marked CUI enters CES, the tool would become a CUI Asset and fall within the CMMC assessment boundary. The advisor's laptop would become an in-scope endpoint requiring all 110 NIST SP 800-171 controls.

**Blast radius:** Limited to the advisor's local machine. Because CES is offline-first with no cloud synchronization, network transmission, or shared storage, the CUI exposure would be contained to a single device's IndexedDB and browser profile. No other advisors, systems, or contractor environments would be affected.

**Mitigation recommendations:**

1. **Training (immediate, high ROI):** Include explicit guidance in advisor onboarding that CES is a planning tool, not a CUI repository. Advisors should never paste marked CUI, SSP excerpts, or controlled technical data into CES input fields.
2. **Policy (immediate, high ROI):** Establish a written data handling policy stating that CES shall contain only compliance metadata and advisor work product, never contractor CUI.
3. **UI warnings (optional, low ROI):** Consider adding informational banners to CES free-text input fields reminding advisors not to enter marked CUI. This provides defense-in-depth but does not substitute for training and policy.

## 9. Tenant-Connected Tools: Scoping Considerations

Three tools built on Stamper core connect to the contractor's GCC High environment. Each warrants separate scoping analysis as a potential External Service Provider (ESP):

**Stamper — Tenant Configuration (BHD Consultant)**

Stamper authenticates to M365 GCC High and Azure Government tenants using certificate-based authentication, establishing pre-authenticated PowerShell sessions across six engine types. It executes commands that modify security controls: deploying Conditional Access policies, configuring sensitivity labels, enabling audit logging, provisioning Sentinel analytics rules. Stamper operates in a limited-time engagement model (connect, configure, disconnect) rather than as a continuous service.

**AdminOps — Operational Management (Customer + BHD Consultant)**

AdminOps uses the same Stamper core engine to manage the tenant operationally. Unlike Stamper's one-time configuration runs, AdminOps supports ongoing tenant management — policy enforcement, configuration drift detection, and tenant health monitoring. Because both the customer and BHD consultant use AdminOps, it has a broader user base and potentially longer-duration access to the tenant.

**EvidenceOps — Assessment Evidence (Customer + BHD Consultant + Assessor)**

EvidenceOps collects and stores evidence artifacts from the contractor's tenant, hashing them with SHA-256 for integrity verification. Its user base is the broadest of the three tools: the customer, the BHD consultant, and the CMMC assessor all use EvidenceOps to generate assessment input. The assessor's direct use of a VFS-built tool during the formal assessment process creates a unique scoping dynamic — EvidenceOps is not just a consultant tool but an assessment instrument.

**ESP Classification**

All three tools likely qualify as ESPs under CMMC scoping rules. ESPs are organizations that provide external system services — including cloud, managed security, and IT management — that process, store, or transmit CUI on behalf of the contractor. Each tool's scoping determination depends on whether its actions affect the confidentiality, integrity, or availability of CUI during execution.

| Tool | Users | Access Pattern | ESP Risk |
|------|-------|---------------|----------|
| Stamper | BHD consultant | One-time config runs | High — modifies security controls |
| AdminOps | Customer + BHD | Ongoing operational | High — continuous tenant access |
| EvidenceOps | Customer + BHD + Assessor | Assessment cycles | High — reads tenant state, assessor-facing |

VFS should evaluate the ESP classification for all three tools with the contractor's CMMC assessor before each engagement.

## 10. Practical Recommendations

Ordered by return on investment for VFS operations:

**Tier 1 — Policy and Training (Implement Immediately)**

1. **Document CES scope exclusion in advisor training materials.** State plainly that CES is an offline planning tool that does not handle CUI and is out of CMMC assessment scope. Advisors should be prepared to explain this to assessors.
2. **Enforce a data handling policy prohibiting CUI in CES.** Written policy should state that advisors shall not enter marked CUI, SSP excerpts containing controlled data, or classified document content into any CES input field.
3. **Prepare advisors for assessor questions about their tools.** Provide the Q&A responses in Section 11 as a reference document for advisors who encounter assessor curiosity about CES during contractor interviews.
4. **Evaluate ESP scoping for Stamper, AdminOps, and EvidenceOps with each contractor's assessor.** Before every engagement, confirm with the CMMC assessor whether each tool's tenant access model requires ESP documentation. EvidenceOps warrants particular attention given the assessor's direct use of it during formal assessment.

**Tier 2 — Optional Technical Enhancements (Defer Unless Requested)**

5. **Consider UI warnings on free-text input fields.** Low-cost informational banners reminding advisors not to paste CUI. Provides defense-in-depth without architectural changes.
6. **Do NOT invest in CES authentication, encryption, or audit logging for CMMC purposes.** These controls provide no CMMC value because CES is out of scope. If VFS decides to implement them for internal security hygiene, that is a separate business decision unrelated to CMMC compliance.
7. **Consider encrypting IndexedDB for tenant config data.** The `tenant_config_profiles` table contains operationally sensitive tenant identifiers and admin account names. Browser-level encryption would protect this data if an advisor's machine is compromised. This is a business security decision, not a CMMC requirement.

## 11. Anticipated Assessor Questions and Responses

The following questions might arise during contractor CMMC interviews if assessors become aware of VFS advisory tools:

**Q1: "Does your consultant's tool have access to your tenant?"**
CES-FE (the Planner) is an offline planning application that runs entirely on the advisor's laptop. It has no network connectivity to contractor tenants, no API credentials, and no remote access capability. However, three separate tools built on Stamper core — Stamper (configuration), AdminOps (operational management), and EvidenceOps (evidence collection) — do connect to the tenant via GCC High. Each serves a different persona and use case.

**Q2: "Where does the compliance tool store data?"**
CES stores all data locally in the browser's IndexedDB database on the advisor's machine. The database is named `CMMCComplianceTool`. No data is stored in the cloud, on shared drives, or on contractor systems.

**Q3: "Can the tool export CUI?"**
CES does not contain CUI. It generates compliance planning artifacts — gap analyses, readiness scores, remediation plans — which are advisor work product, not controlled information. Exported mission plans contain implementation instructions, not CUI.

**Q4: "Is the advisor's laptop part of our CMMC boundary?"**
No. The advisor's laptop is not a CUI Asset, Security Protection Asset, or Contractor Risk Managed Asset. It does not process, store, or transmit your CUI. It is consultant equipment used for compliance planning.

**Q5: "What if the advisor accidentally stores CUI in the tool?"**
VFS maintains a data handling policy prohibiting advisors from entering marked CUI into CES. In the unlikely event of a policy violation, the exposure would be limited to a single advisor's local machine with no cloud propagation. VFS would remediate by clearing the advisor's local database and retraining the advisor.

**Q6: "Does the tool connect to any cloud services?"**
CES-FE loads static reference data (YAML question banks and JSON validation schemas) from its own application directory. It makes no calls to external cloud services, APIs, or contractor systems.

**Q7: "How does the tool generate the mission plan that gets executed against our tenant?"**
CES generates mission plans through an offline workflow: advisors answer structured question banks, CES evaluates the answers against CMMC L2 requirements, and it produces a JSON artifact containing remediation steps mapped to specific controls. This artifact is then provided to Stamper for execution, while AdminOps handles ongoing operational management and EvidenceOps generates assessment evidence. The handoff from CES to the tenant-connected tools is a file transfer, not an API integration.

**Q8: "Is the tool FedRAMP authorized?"**
CES does not require FedRAMP authorization because it is not a cloud service and does not process CUI. It is a local desktop application. FedRAMP applies to cloud service providers handling federal data.

**Q9: "Who else can see the data in the tool?"**
Only the advisor using the specific browser profile on their machine. CES has no multi-user features, no shared databases, and no cloud synchronization. Each advisor's CES instance is isolated to their local device.

**Q10: "What happens to the data after the engagement?"**
VFS advisors can clear all customer data from CES using the built-in database reset function. This removes all records from IndexedDB. VFS data retention policies govern when advisors must purge engagement data from their local machines.

## 12. Conclusion

CES-FE is an offline compliance planning tool that operates entirely on the VFS advisor's workstation. It does not process, store, or transmit CUI. It does not connect to contractor tenants. It does not function as a Security Protection Asset. By every measure of CMMC L2 scoping methodology, CES is out of scope for assessment.

The architectural boundary between CES and the contractor's CMMC perimeter falls at the tenant connection point — the moment Stamper, AdminOps, or EvidenceOps authenticates to M365 GCC High or Azure Government. Everything upstream of that point is advisor-side planning activity.

VFS should focus compliance hardening efforts on ESP scoping for all three tenant-connected tools (Stamper, AdminOps, EvidenceOps), not CES tooling. The highest-value investments are advisor training, data handling policies, and pre-engagement scoping conversations with each contractor's CMMC assessor. Technical hardening of CES (authentication, encryption, audit logging) provides no CMMC benefit and should be deferred unless driven by separate internal security requirements.
